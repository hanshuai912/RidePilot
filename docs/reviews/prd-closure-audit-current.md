# PRD 业务闭环复核

复核基线：开发仓库 `a260a6d`，产品基线为 [PRD](../../RidePilot_Product/PRD.md)。审查时只增加报告；后续落实情况另在各条目中记录，不改写历史审查结论。

这是对 [上一轮审计](prd-gap-audit-2026-11-04.md) 的增量复核。旧报告中的“跨周备赛缺失”“训练补给联动未接入”“没有移动端自由问答”“没有待处理建议入口”“缺少周期复盘”等结论已不适用于当前代码。以下优先级是建议开发顺序，不改变 PRD 的 P0/P1 划分。

## 当前已经接上的主链路

- 建档、FTP、可训练时间 → AI 或手动课程草稿 → 校验、预览、确认 → 正式训练版本。
- 独立阶段安排 → 主动安排测试 → 结果、可比历史和复评 → 用户选择范围生成后续课程；FTP 另外确认更新。
- 赛事新增、改期、取消、结果 → 自选跨周范围备赛、恢复或回归目标草稿 → 确认应用；关联旧任务和未应用草稿失效。
- 训练变更 → 待核对补给 → 用户主动生成、份量/时间编辑、逐日预览 → 独立确认营养版本。
- 教练状态依据、自由问答、建议恢复/放弃、重复生成复用、失效历史，以及训练执行与周期复盘 → 后续训练。

对应实现和边界见 [赛事](../features/races.md)、[营养](../features/nutrition.md)、[教练中心](../features/ai-coach-center.md)、[建议生命周期](../features/coach-suggestion-lifecycle.md)、[周期复盘](../features/training-cycle-review.md)。这些能力已有代码及测试基础，不应再按整块未开发安排任务；本次没有证明真机与真实模型端到端全部通过。

## 建议优先补齐的业务闭环

### 1. 目标生命周期和阶段达成判断

**后续落实（2026-11-06）：** 已补充独立新建目标、变更预览、暂停/恢复/延期/完成/结束/下一目标、主次切换事务，以及阶段达成条件、用户复评决定、证据历史和绑定后续阶段/课程草稿。到期目标在周期复盘可进入管理。详见 [实现、验证及边界](../features/goal-lifecycle-stage-review.md)。自动达成阈值、通用指标体系与真机/真实模型验收仍保留。下列断点为本次审查时的原始记录。

关联 PRD：M02 FR-101～106、M05 FR-405～406、M11、§3.5.7。

**当前断点：**

- 目标有服务端修改及 ACTIVE/PAUSED/CLOSED 状态，但移动端主要是查看和修改当前活跃目标，缺少明确的暂停、恢复、结束和新建下一目标操作。
- 目标指标主要是可选 `targetWkg`，没有完整表达不同目标的基线、目标值、单位、验证方式。难度评估和多目标冲突处理尚未形成产品流程；建档保存固定 PRIMARY。
- 阶段包含日期、目的和测试建议；“当前/已结束”由日期决定，没有独立的达成条件、评估结果及用户确认的阶段决策记录。已有测试比较和课程执行统计，不等于已经判断阶段达成。
- 周期复盘可以继续生成课程，但后续范围不能超过目标日期。目标到期或整个阶段安排结束后，尚缺少就地选择延期、调整目标或建立下一目标的完整引导。

**建议闭环：** 目标与可观察指标 → 定性难度/不确定性说明 → 阶段验证条件 → 测试及训练证据 → 保持/延长/调整/进入下一阶段的建议 → 用户确认 → 后续草稿；目标完成或到期后可结束、延期或创建下一目标。阶段不得自动晋级，未确认的测试协议和达成阈值仍需产品决策。

**验收例：** 目标日期已到且无后续课程时，用户能选择下一步并生成可执行草稿；缺少有效测试时显示证据不足；暂停/恢复和多目标取舍不会静默改写正式课程。

证据：[目标契约](../../packages/contracts/src/coach.ts)、[阶段契约](../../packages/contracts/src/stages.ts)、[目标详情](../../apps/mobile/src/features/goals/screens/GoalDetailScreen.tsx)、[阶段时间线](../../apps/mobile/src/features/goals/components/StageTimeline.tsx)、[目标保存](../../apps/mobile/src/features/coach/hooks/useInitialPlan.ts)、[测试复评](../../apps/api/src/modules/coach/assessment-review.service.ts)。

### 2. 修改目标、FTP、可用时间后的未来计划处理

关联 PRD：FR-006、FR-104、AC-M02、§11 FTP 变化场景。

**本次实现：** 已统一串起保存资料后的影响检查、按日期范围保留、FTP 重算草稿、范围重排预览与确认、任务恢复及补给待核对。新增课程资料/FTP 快照和持久处理决定；旧课程没有依据时明确标注未知，不能直接重算。阶段和测试仍通过已有目标/复评流程独立确认。实现与验证见 [资料变更闭环](../features/plan-input-impact.md)。

**建议闭环：** 保存新事实 → 说明未来影响及待检查事项 → 选择保留当前安排或主动重算/重排 → 预览旧新功率、时长、日期与受影响阶段 → 用户确认 → 新正式版本 → 提示核对补给。

**验收例：** FTP 从 200 W 改为 220 W 后，展示按原 FTP 快照与新能力计算的未来强度差异；拒绝更新未来计划时明确提示旧安排仍在执行；已完成记录与旧版本保持可追溯。修改可训练日后不静默移动课程。

证据：[FTP 保存](../../apps/mobile/src/features/profile/hooks/useFtpEditor.ts)、[资料与目标写入](../../apps/api/src/modules/coach/coach-data.service.ts)、[阶段失效提示](../../apps/api/src/modules/coach/coach-overview.service.ts)、[建议有效性](../../apps/api/src/modules/coach/coach-suggestions.service.ts)。

### 3. 历史版本恢复到 App

关联 PRD：FR-309、FR-905、AC-M10。

**当前断点：** 后端已有版本列表、详情和恢复提案；教练中心也能展示最近版本，但移动端没有版本详情比较、恢复草稿和确认应用入口。建议中心训练类型列表也没有 PLAN_RESTORE，不能直接依靠现有 AI 建议列表完成恢复。

**建议闭环：** 版本列表 → 查看当时内容 → 选择恢复 → 展示今天起可恢复的课程和保留的记录 → 校验/确认 → 新版本 → 返回日历。恢复失败保留原正式计划；不能恢复已经过去的执行日程。

**验收例：** v3 → 应用 v4 → 选择恢复 v3 的未来内容 → 创建 v5；历史记录保留，重复提交幂等，另一端已发布新版本时提示冲突。

证据：[恢复 API](../../apps/api/src/modules/coach/plan-restore.controller.ts)、[恢复服务](../../apps/api/src/modules/coach/plan-restore.service.ts)、[建议类型筛选](../../apps/api/src/modules/coach/coach-suggestions.repository.ts)、[版本展示](../../apps/mobile/src/features/coach/components/CoachOverviewPanel.tsx)。

### 4. 训练反馈的更正，以及不同调整入口读取相同事实

关联 PRD：FR-702～705、§3.5.2/3.5.5。

**当前断点：**

- 反馈目前支持完成状态、时长、RPE、疲劳和备注，缺少结构化睡眠/恢复、疼痛/异常及可选距离、功率、心率字段。
- 已有记录时客户端禁止再提交，服务端返回 ACTIVITY_ALREADY_RECORDED；缺少显式更正记录、版本冲突和更正留痕流程。填错反馈后会持续影响下一课程筛选和状态判断。
- 周期复盘已将真实执行和疲劳依据交给生成；普通周调整/单节调整没有统一加载同一份近期反馈摘要，主要依赖本次输入或指定的单条事件。不能把“复盘已接入证据”理解为所有生成入口都已接入。
- 静态代码还显示：训练记录日期固定等于课程计划日期，没有实际执行日期选择，也未见记录接口禁止未来日期。提前做、补做或误将未来课标记完成的语义需明确并验证，不能依赖用户自行避开。

**建议闭环：** 真实执行日期与反馈 → 保存 → 可追溯更正 → 状态/复盘重新读取 → 相关未应用草稿失效 → 用户主动决定是否重规划；所有调整入口读取统一事实。保存或更正记录不得自动改正式计划。

**验收例：** 将误填疲劳 9 改为 3 后，概览与复盘更新，基于旧依据的候选不能继续应用；未来日期不能伪装成已发生训练。缺数据时说明依据不足，不以 RPE 替代疲劳。

证据：[反馈契约](../../packages/contracts/src/coach.ts)、[反馈 hook](../../apps/mobile/src/features/training/hooks/useWorkoutFeedback.ts)、[记录写入](../../apps/api/src/modules/coach/coach-events.service.ts)、[生成上下文](../../apps/api/src/modules/coach/coach-generation-context.service.ts)、[复盘规则](../../apps/api/src/modules/coach/cycle-review/cycle-review.policy.ts)。未来记录行为本次为静态发现，未做实际数据库复现。

### 5. 让预览支持真正比较和继续编辑

关联 PRD：FR-305～307、FR-313、FR-007、§6.2/6.3。

**当前断点：** 单节 AI 预览主要比较标题、日期和动作数；通用预览能展开新课程，但旧课程主要只列日期和标题，缺少逐项时长、距离、强度、目的变化的对照。已有训练补给联动，仍需在预览说明其影响。AI 候选局部编辑接口未接通移动端；“继续修改”返回生成条件，不能等同于编辑已生成候选。手动动作列表有排序图标但没有排序回调；简洁/专业视图及偏好也未落地。

**建议闭环：** 看懂旧新差异 → 在候选中调整动作/顺序/日期 → 重新校验 → 明确只改本节或联动后续 → 再确认范围 → 应用。双视图共享同一草稿，切换不丢参数。

**验收例：** 90 分钟阈值课改为 45 分钟恢复骑，预览明确展示时间及目的改变；编辑候选后旧校验失效；调整动作顺序实际改变结构；取消时正式计划不变。

证据：[单节预览](../../apps/mobile/src/features/training/components/WorkoutAdjustmentPreview.tsx)、[通用预览](../../apps/mobile/src/features/coach/components/PlanPreview.tsx)、[候选 API](../../apps/api/src/modules/coach/ai-proposal.controller.ts)、[动作列表](../../apps/mobile/src/features/training/components/WorkoutSegmentList.tsx)、[手动编辑器](../../apps/mobile/src/features/training/components/Editor.tsx)。

### 6. 首页与日历统一行动入口

关联 PRD：FR-202/204、P03、§6.1、M11。

**当前断点：** 日历已经展示课程、测试和比赛，仍只有周视图，没有明确休息/恢复事件及完整课程改期、冲突原因和替代日期流程。首页聚合训练和营养，身体状态卡仍固定显示待评估；教练页已存在的状态依据、下一测试、待处理草稿等没有聚合回首页，下一比赛也未接入。

**建议闭环：** 首页知道今天该做什么、下一测试/比赛和待确认事项 → 进入真实详情或调整 → 预览确认 → 返回后同步更新。月历和休息事件共用实际数据；日期以账号时区一致解释。

M11 已有周期复盘中的完成率、时长、RPE/疲劳和最近 FTP 比较，不再列为“没有分析”。剩余重点是目标差距、阶段达成与跨周期趋势，以及统计口径：当前复盘已明确不追溯被替换且没有反馈的历史课程，若后续做长期完成率，需先定义计划分母的历史快照规则。

证据：[首页聚合](../../apps/api/src/modules/home/home.service.ts)、[固定状态卡](../../apps/mobile/src/features/home/components/HomeStatusCard.tsx)、[训练日历](../../apps/mobile/src/features/training/screens/TrainingScreen.tsx)、[周期复盘说明](../features/training-cycle-review.md)。

## 已部分闭环但需统一产品口径的内容

1. **训练、阶段、测试和营养分别确认还是一次应用。** 当前训练与营养已能串行联动、显示待核对，并不是缺联动。但 PRD M10 仍要求可勾选营养一起应用，赛事验收也要求更完整的关联对比；实现明确不提供跨领域原子应用。应先统一口径：若 V1 保持分别确认，更新 PRD 验收；若保留一次应用，则需统一变更集、预览、版本校验及全体成功/失败事务。
2. **相近赛事的取舍和测试调整。** 当前影响预览已列出范围内其他赛事、测试和阶段；模型参考赛事优先级，课程避开赛事和测试日。剩余是具体取舍及可执行的测试顺延/替代方案，不应再描述为“只看比赛当天冲突”。恢复间隔和达成阈值仍待确认，不能自行发明固定处方。
3. **生成取消。** 当前离开页面停止轮询，服务端继续生成，可恢复结果；这与放弃一份已存在草稿不同。PRD §12.2 的可取消生成还需定义排队撤销、运行结果废弃、取消后重试及是否能停止供应商请求。
4. **全部周期重规划。** 教练快捷入口的 CYCLE 仍提示暂未开放；目标详情和周期复盘已经支持自选范围。应优先复用范围生成，避免再建一套；1–84 天课程、365 天阶段是已记录的实现限制，不应把超长一次生成误报为 V1 必须新增的能力。

## 正式发布前的独立阻塞项

- **真实 AI 安全审核及可启动的 production 配置。** 当前输入输出审核只装配 NoopGuard，始终 ALLOW；环境 schema 只允许 `AI_GUARD_MODE=noop`，production 又拒绝该值，因此按仓库当前配置 production 无可用取值，API 会在启动校验时失败。结构化症状阻断、JSON 和领域校验已存在，不能替代真实输入输出审核。应实现真实适配器及故障策略，再验证生产配置启动、正常问题通过、风险请求阻断和审核不可用时降级。
- **隐私授权与数据生命周期。** “我的”仍说明导出/删除尚未开放；需要 AI/敏感数据使用授权记录、导出/删除入口及明确处理结果。适用市场、年龄及保留规则按 PRD 待确认项决策。
- **AI 和关键写接口运行保障。** 已有鉴权限流、任务去重、超时和用量日志；仓库内未见完整 AI/应用限流、用户配额/预算和异常告警链路。仓库外网关配置本次未核实，不能据此断言线上也不存在。完整业务审计与 PRD 埋点也需单独验收。
- **发布验收。** 真实短信及测试账号迁移仍是待决策事项；测试验证码不是已完成的生产注册。真机核心链路、真实模型质量、数据库并发/事务、备份恢复和部署环境需要对应实测，不能用普通 Jest 通过替代。

证据：[审核装配](../../apps/api/src/ai/ai.module.ts)、[Noop 审核](../../apps/api/src/ai/guardrails/noop-guard.adapter.ts)、[环境约束](../../apps/api/src/config/env.ts)、[隐私入口](../../apps/mobile/src/features/profile/screens/ProfileScreen.tsx)、[鉴权限流](../../apps/api/src/modules/auth/auth-rate-limit.service.ts)。

## 建议拆分顺序与完成标准

建议业务开发顺序：目标生命周期/阶段验证 → 资料变化的未来影响 → 版本恢复入口 → 反馈更正与统一生成证据 → 候选编辑/差异预览 → 首页与统一日历。真实审核和隐私路径应在面向真实用户发布前完成；它们不以完成全部体验增强为前提。

每个任务独立交付：真实入口、主流程、取消/返回、空状态、重试、归属、并发版本、幂等、失效草稿、历史保留、确认应用及对应功能文档。高级模板、图表导出、全面设备同步属于 P1/P2，不混入这些 V1 缺口。
