# 赛事管理与备赛流程

## 目的与范围

实现 PRD M07 的第一版闭环：保存赛事事件、查看训练冲突、生成备赛训练草稿、预览并应用，以及录入赛后结果。赛事元数据保存不会直接修改正式训练计划；训练变化继续复用 `RACE_REPLAN` 提案和正式版本应用事务。

## 用户流程

1. 从训练页进入赛事管理，创建或编辑赛事。
2. 赛事保存后读取比赛当天的课程、阶段测试和其他赛事冲突。
3. 用户进入备赛草稿，服务端读取当前目标和正式计划版本，异步生成 `RACE_REPLAN` 提案。
4. 用户查看课程替换、阶段说明和影响日期，先校验，再确认应用。
5. 比赛结束后录入完成状态、实际日期、用时、RPE、疲劳和备注。结果保存不会自动改变训练；后续可从 AI 教练生成赛后恢复草稿。
6. 赛事详情可单独生成赛前、比赛中和赛后补给草稿；营养草稿经过独立校验和确认后应用。

## API

| Method | Path                         | 用途                       |
| ------ | ---------------------------- | -------------------------- |
| GET    | `/races`                     | 当前用户赛事列表           |
| POST   | `/races`                     | 创建赛事事件               |
| GET    | `/races/:id`                 | 读取赛事                   |
| PATCH  | `/races/:id`                 | 版本化修改或取消赛事       |
| GET    | `/races/:id/impact-preview`  | 读取比赛当天冲突和影响日期 |
| POST   | `/races/:id/replan-proposal` | 生成备赛训练提案           |
| GET    | `/races/:id/result`          | 读取赛后结果               |
| POST   | `/races/:id/result`          | 创建或版本化更新赛后结果   |

## 数据与规则

- `TrainingRace` 增加赛事类型、预计爬升和参赛意图；现有数据使用公路赛、稳妥完赛默认值兼容。
- `TrainingRaceResult` 独立保存实际结果，和计划赛事一对一关联。
- 赛事修改使用 `expectedVersion`；已完成赛事不能修改赛事元数据。
- 赛后结果写入时锁定用户，检查赛事归属和结果版本，并将赛事状态更新为 `COMPLETED`。
- 影响预览是确定性冲突读取；AI 只生成候选训练安排，正式计划仍需校验和用户确认。
- 训练与营养版本目前分别应用；赛事详情提供两个独立草稿入口，跨领域一次性原子应用仍待后续实现。

## 移动端

- `/races`：赛事列表。
- `/races/new`、`/races/edit`：赛事表单。
- `/races/[raceId]`：赛事详情、冲突预览和赛后结果。
- `/races/proposal`：备赛提案生成、校验和应用。
- `/races/training-setup`：补齐备赛基本信息，返回同一赛事后手动生成。
- `/races/nutrition-proposal`：赛事补给提案生成、校验和应用。
- 训练页增加赛事管理入口。

## 草稿生成 loading 修复（2026-11-04）

- 备赛与赛事补给页面原先把 `started` 状态放进 `useFocusEffect` 的回调依赖。启动时执行 `setStarted(true)` 会触发旧回调清理，将 `active` 置为 `false`；后续成功、错误和 `finally` 都不能更新页面，导致永久 loading。
- 两个页面移除该状态依赖，以赛事 ID、登录 token、恢复模式（仅备赛）和显式重试次数控制生成流程。生成开始时清空旧草稿及错误；失焦、卸载或参数变化后忽略旧任务结果，再次聚焦时重新开始。
- 备赛生成复用 `waitForCoachProposal`，赛事补给继续复用 `waitForNutritionProposal`，统一处理排队、运行、失败、缺失草稿和等待超时。单次请求继续使用现有 API 超时保护；轮询上限为 100 轮、每轮间隔 1.5 秒（不含请求耗时）。
- 生成失败时显示错误及“重试”入口。只有用户确认后才应用草稿。本次无 API、契约或数据库变化。
- 回归测试：`apps/mobile/src/features/races/__tests__/race-proposal.test.tsx`，覆盖成功展示、失败提示与重试、轮询完成与超时、卸载停止轮询、缺少目标或正式计划、切换赛事旧结果隔离，以及失焦后返回。
- 验证命令：`pnpm --filter @ridepilot/mobile test`（24 套、217 项通过）；补充失焦测试后运行 `pnpm --filter @ridepilot/mobile test -- --runTestsByPath src/features/races/__tests__/race-proposal.test.tsx`（13 项通过）；`pnpm test`（17 套、77 项通过，9 套、45 项跳过）；`pnpm build`（通过）；`pnpm typecheck`（通过）；`pnpm lint`（退出码 0，无错误，两个 `retryCount` 依赖警告；该依赖用于显式重试时重启生成流程）。
- 人工验收：分别从赛事详情进入备赛和赛事补给草稿，确认 loading 能转为草稿预览；模拟网络失败后显示错误并能重试；生成期间离开页面再返回，确认页面不会永久停留在 loading。

## 赛事补给生成链路修复（2026-11-04）

- 后续排查发现最近五次 `RACE_LINKED` 任务均已失败，错误为 `AI_PROVIDER_INVALID_RESPONSE` 或 `AI_OUTPUT_INVALID`，因此生命周期修复并不足以保证实际模型能生成有效草稿。
- 实际调用复查显示，多日草稿连同模型推理会消耗超过固定 7,000 token 的额度；提高额度后还复现了 `draft` 出现契约外字段的问题。服务端对赛事场景按 `5000 + 天数 × 3000` 分配额度（最少 7,000、最多 32,000；五天为 20,000），明确禁止附加字段，补给策略写入已有餐次、备注、摘要和假设中。严格 schema、领域校验和用户确认保持必需。
- 生成生命周期拆分为 `hooks/useRaceNutritionDraft.ts` 与 `services/race-nutrition-draft.ts`。页面展示读取资料、排队和生成校验三个阶段，允许等待期间返回；不再只展示通用的“训练数据加载中”。
- 对读取、提交、轮询和草稿下载设置 180 秒整体等待保护，轮询采用约 150 秒实际时间预算（正在进行的单次请求仍受 12 秒请求超时约束），避免只按轮数计时而忽略请求耗时。模型失败、无效响应、网络错误均显示可重试错误。
- 页面仍挂载时，失焦后返回、登录 token 刷新，以及查询超时/网络失败后的重试，复用原来的生成任务；仅提交失败或后台明确失败时才创建新任务。整体等待超时不会取消后台任务，也不会应用正式计划。
- 服务端仅对可重试的模型异常和结构校验失败自动重试，避免对不可重试的无效响应重复排队。本次未修改 API 形状、共享契约或数据库，无需迁移。
- 真实模型复查仅使用只读上下文并截断持久化步骤，没有修改现有任务或正式计划；五天赛事输入约 90 秒返回 15 个餐次，严格共享契约校验通过。
- 新增 `race-nutrition-routes.test.tsx`：使用真实 Expo Router、真实页面组件，从赛事详情点击入口验证草稿展示、排队到运行再到失败、错误重试、请求不返回时整体超时、失焦后恢复、轮询超时后复用任务。结合既有草稿测试，18 项通过。
- 最终验证：`pnpm --filter @ridepilot/mobile test`（25 套、222 项通过）；`pnpm test`（17 套、80 项通过，依赖外部环境的 9 套、45 项按既有配置跳过）；`pnpm typecheck`、`pnpm build`、本次修改文件的 `pnpm exec prettier --check ...`、`git diff --check` 均通过；`pnpm lint` 退出码 0，保留备赛训练页原有的一条 `retryCount` 依赖警告，赛事补给页无警告。真机操作尚未验证；实际模型诊断未测试数据库落库事务。

## 已应用方案恢复与显式重新生成（2026-11-04）

- 修复应用后再次点击赛事补给入口会自动重新生成的问题。此前仅在页面挂载期间保存任务引用，退出页面后没有按赛事恢复服务端结果。
- 新增 `GET /nutrition/races/:raceId/proposal` 和共享 `raceNutritionStateSchema`。通过现有 `AiGeneration.input.raceId` 关联赛事、任务和营养提案，无需新增表或迁移，历史已生成/已应用数据可直接读取。
- 服务端优先返回当前正式营养版本对应的已应用赛事提案，即使误操作曾生成更新的普通草稿，也不隐藏已应用方案。无已应用方案时恢复有效草稿或当前版本的排队/运行任务。所有查询都验证赛事归属并按用户过滤任务与提案。
- 赛事详情根据状态显示“生成赛事补给草稿”“继续生成赛事补给草稿”“查看赛事补给草稿”或“查看赛事补给方案”。已应用方案显示“已应用”，不提供再次校验或应用按钮。
- 页面内提供“重新生成赛事补给”，仅此明确操作发送 `forceRegenerate: true`。新建议保持草稿状态，正式饮食计划只有在用户确认应用后才替换。显式请求的新草稿或任务优先恢复，离开再返回可继续处理。
- 普通生成请求复用已有结果；显式重新生成仅在没有相同赛事的显式运行任务时创建新任务。用户行锁与事务保护查询/创建，保持幂等键校验，避免并发重复提交。
- 赛事更新前的任务、过期草稿和基于旧营养版本的未应用草稿不复用；既有错误提示、整体超时和查询重试机制保留。
- 已执行专项测试：API 的 `race-nutrition.spec.ts`、`race-nutrition.e2e-spec.ts`、`nutrition-generation.spec.ts` 共 21 项通过；移动端赛事路由、草稿生命周期和饮食页共 25 项通过。覆盖应用后重新进入、冷启动恢复、显式重新生成不自动应用、401/404、过期草稿、重复提交及显式任务恢复。
- 最终验证命令：`pnpm --filter @ridepilot/mobile test`（25 套、226 项通过）；`pnpm test`（19 套、95 项通过，9 套、45 项按既有外部环境条件跳过）；`pnpm typecheck`、`pnpm build`、`git diff --check` 均通过；`pnpm lint` 无错误，保留备赛训练页既有的一条依赖警告。真机操作及真实数据库并发写入测试未执行。
- 使用现有数据执行新查询服务的只读诊断：返回 `APPLIED` 方案，共享契约校验通过，诊断前后生成任务数变化为 0。没有重新调用模型或更改正式计划。

## 空白时段备赛、资料补填与手动生成（2026-11-04）

- 进入备赛页、补填返回和重新聚焦均只读取赛事、目标、计划版本与 readiness；必须点击“生成备赛计划草稿”才提交生成任务。失败后显示“重新生成备赛计划草稿”，不由页面自动创建新任务。
- 继续使用赛事所在周（周一至周日）的现有范围。无正式计划时以版本 0 创建草稿；已有正式计划但该周为空时追加课程；有可调整课程时只替换该周未来且无训练记录的课程。历史课程、已记录课程和范围外课程保留，仍需用户预览确认并通过正式版本事务应用。
- 缺少 FTP、训练经验、训练目标、每周可训练时间或功体比目标所需体重时，展示缺失项与“去填写基本信息”。`RaceTrainingSetupScreen` 复用现有资料表单及保存逻辑，按缺失项引导；FTP 和体重跳转已有资料页面，返回后刷新。补填完成点击“返回备赛计划”，保留赛事 ID 与恢复模式，再由用户手动点击生成。
- `useRaceTrainingDraft` 单独管理资料检查、手动提交、轮询、错误和生命周期。提交前重新读取版本与 readiness，处理补填期间的计划变化，以及服务端返回的缺失字段。日期按日期字符串的 UTC 运算定位周一，不受设备时区偏移影响。
- 修复 `INSUFFICIENT_RECOVERY` 的生成约束缺失：校验器按 work 区段强度上限达到 90% FTP 判定高强度日，短暂赛前激活也计入。请求明确禁止相邻自然日安排这种课程，赛事参考指令同步说明。安全校验保持严格；一次用户提交的任务若首次返回恢复不足，可在原任务内携带校验反馈纠正一次，第二次仍不合规则失败，不创建正式课程。页面显示中文错误，后续新任务由用户手动触发。
- API 请求/响应形状与数据库结构不变；仅赛事场景允许没有可替换课程，不放宽普通调整入口的限制。没有剩余可训练日期、归属不符、版本冲突仍拒绝。
