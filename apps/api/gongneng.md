## 一、项目背景

这是一个面向中国大陆用户的 AI 运动训练 App。

技术栈：

- 前端：React Native + Expo + TypeScript
- 后端：NestJS + TypeScript
- 项目结构：Monorepo
- AI 模型：需要支持多个供应商，不绑定某一家模型
- V1 运动类型：公路自行车
- 后续支持：跑步、其他耐力运动

产品的主要功能：

1. 根据运动员个人资料、目标、训练历史和可用时间生成训练计划。
2. 根据疲劳、恢复、训练完成情况等信息动态调整计划。
3. 支持 AI 辅助修改训练课程。
4. 根据阶段测试、临时赛事与训练反馈更新训练建议。
5. 用户可以预览 AI 修改结果，确认后应用。
6. AI 交互以结构化操作为主，不依赖自由聊天。

当前仓库已存在统一 `AiService`、Provider Adapter、Guard 接口，以及仅支持单节手动课程的 `ChangeProposal` / `PlanVersion` 应用链路。仍须以实际代码复核；尤其不能把开发环境的 Noop Guard 当作真实内容审核。目标、可训练时间、FTP 录入、阶段测试、赛事及训练记录等业务能力若尚未实现，应在本任务内补齐支撑 AI 闭环的最小实现。

## 三、架构目标

保持通用 Skill Engine 与训练业务编排两层边界；正式计划的持久化仍交给现有训练/提案模块，不交给 Skill 或模型。

### 第一层：通用 Skill Engine

用于管理和执行 AI Skill，不包含骑行、跑步等具体业务规则。

建议的核心职责：

**SkillRegistry**

- 注册和管理 Skill
- 支持 Skill ID、版本、名称、描述
- 支持能力标签、启用状态
- 支持按 ID 查找

**SkillLoader**

- 加载本地 SKILL.md
- 加载 references 参考知识文件
- 按需读取，避免将所有 Skill 内容一次性加入上下文
- 限制文件访问路径、大小和数量
- 支持对 Skill 内容进行版本管理

**SkillExecutor**

- 接收 Skill ID、业务上下文和目标输出 Schema
- 加载对应 Skill 指令
- 组合系统指令、Skill 内容和业务数据
- 调用现有 AI Gateway
- 解析结构化响应
- 校验返回结果
- 统一处理错误和执行日志

本任务采用受控的服务端 Skill，不需要自主 Agent 框架。Skill 执行结果必须携带 Skill ID、版本或内容摘要，以便回溯建议来源。

不允许 Skill 任意执行本地脚本、操作数据库、访问外部网络或者调用未经授权的工具。

第三方 SKILL.md 必须作为经过审查的领域知识与工作流程使用，不得让其覆盖系统安全约束。

### 第二层：AI Training Module

负责具体的训练业务编排。

建议包含以下职责：

**TrainingAIOrchestrator**

- 按场景接收首份计划、滚动周计划、单节课程调整、周计划调整、阶段复评与赛事重规划请求
- 检查当前用户权限及前置资料，选择适用 Skill，调用统一 AI Gateway
- 将模型候选交给领域校验，保存为可预览提案；绝不直接更新正式计划

**TrainingContextBuilder**

- 从服务端数据源获取 FTP 测量值及来源/日期、运动经验、目标与阶段、可训练时段、当前正式计划、实际训练记录、主观疲劳/恢复、测试结果与赛事
- 按用户时区构建结构化、最小必要上下文；记录输入版本或快照以检测预览后的变化
- 缺少本场景的必要字段时明确列出，不能虚构训练历史、测试结果或恢复状态

**TrainingPlanGenerator**

- 生成首份近期周计划和阶段路线，按阶段测试或反馈滚动生成后续周计划
- 使用对应的 Cycling Skill，输出符合共享 Schema 的结构化候选

**TrainingAdjustmentService**

- 支持时间不足、疲劳/睡眠差、天气、临时占用、课程太难、未完成训练等快捷原因
- 对单节课程或所选未来日期范围提出 1～3 个可比较方案，解释训练目标是否改变、受影响课程和恢复安排
- 不机械补齐错过的高强度课，不编辑已完成的实际训练记录

**AssessmentReviewService / RaceReplanService**

- 阶段测试结果录入后评估目标与阶段，提出继续、调整、延期或恢复建议，并生成未来计划草稿
- 比赛新增、改期、取消及 A/B/C 优先级变化时检查训练、测试、恢复与其他赛事冲突，形成备赛或回归训练草稿
- 已确认赛事和测试的变更及跨领域影响必须在差异预览中呈现；只在用户确认后写入正式版本

**CoachExplanationService**

- 提供计划解释和自由问答；快捷结构化动作仍是主要入口
- 对话默认只读，不通过聊天文本直接应用训练计划；若需要修改，显式转入对应提案流程

**TrainingPlanValidator**

- 校验 Schema、目标日期/用户时区、区段汇总、FTP 强度、可用时段、课程与赛事/测试冲突、训练负荷与恢复边界
- 确定性 FTP 功率换算、时间/距离汇总、重复区段展开由 TypeScript 完成
- 按错误严重程度返回阻断项、需确认警告和说明；明显危险建议必须阻断

以上均为职责建议，不要求机械创建同名文件或类。按现有模块组织，避免一个巨型 Service。饮食 AI 仅保留未来接入边界，本任务不生成可应用的饮食建议。

## 五、本任务需要实现的训练业务闭环

### 5.1 共用前置资料与计划状态

1. 用户可录入、查看和更新 FTP 测量值（W、测量日期、来源），并能设置正式训练目标、期限/优先级、每周可训练时间、休息日与单次时长限制。只补本任务需要的最小业务接口和数据模型；资料归属服务端校验。
2. AI 教练入口通过**正式计划状态接口**判断是否有正式计划，不以本周日历为空代替。无计划时展示建计划引导，并保留“先手动创建一节训练”的既有入口。
3. 生成/调整前返回资料就绪状态与 `missingFields`。FTP 必填且须从服务端当前用户的有效测量值读取；目标、可训练时间、用户时区及本场景必要反馈缺失时给出补录路径。目标若填写 `targetWkg`，还必须提供当前体重，服务端将目标功体比换算为目标 FTP 功率；体重变化使未应用提案过期。非必要的历史数据缺失要标注置信边界，不得伪造。

### 5.2 首份计划与滚动周计划

1. 用户完成资料后，从移动端发起近期一周骑行计划生成；已有计划的用户可以为**尚无课程的未来周**生成下一周计划。包含已有课程的周不得被静默覆盖。
2. 服务端构建最小上下文，加载 `cycling-training` Skill，通过统一 AI Gateway 生成结构化课程、阶段路线与阶段测试建议。
3. 训练规则校验通过后，保存整周**一个**提案。客户端查看每节课程、休息安排、测试节点、目标与影响范围，必要时修改候选内容并重新校验。
4. 用户明确确认后，原子创建首份正式计划第 1 版或已有计划的新版本；放弃或生成失败时正式计划保持不变。
5. 后续按训练完成情况、阶段测试和目标变化滚动生成未来周计划，不一次性生成无法维护的长期每日课程。

### 5.3 AI 课程与计划调整

1. 从课程详情、训练日历和 AI 教练快捷入口进入“时间不足、疲劳/睡眠差、天气、出差/加班、训练太难、未完成”等场景；用结构化字段收集必要信息，自由短描述只作补充。
2. 支持“仅本节”和“联动未来一周/当前阶段”两种范围；后者要展示受影响日期、课程、测试与恢复安排。模型可给出 1～3 个候选，说明保留或改变原训练目的的取舍。
3. 用户可选择或编辑候选；服务端重新校验后进入差异预览。取消、失败或超时不改变已应用版本。已完成的实际训练记录不得被计划修改覆盖。
4. 连续无法完成高强度课程、疲劳明显或危险症状时采取保守路径；危险症状不继续生成可应用的高强度方案。

### 5.4 训练反馈、阶段测试与目标复评

1. 用户可记录完成、部分完成或跳过，实际时长、RPE、疲劳/恢复和原因；实际记录与计划课程独立保存。
2. 支持建立目标及阶段、安排适合设备条件的测试、录入结果与条件，允许延期、跳过和标记无效。FTP 更新保留测量历史，不覆盖旧值来源。
3. AI 根据实际反馈和可比较的测试结果解释阶段进展，生成继续、调整、延期、恢复或重新评估目标的**候选**下一阶段计划。不能承诺确定提升幅度。
4. 阶段或目标变化只修改未来计划，并展示原方案、建议方案及依据；用户确认后才能生效。

### 5.5 赛事变动与备赛

1. 用户可新增、改期、取消比赛并设置 A/B/C 重要性、日期/时区、类型和距离；赛事本身为独立业务事件，AI 负责评估其训练影响。
2. 对赛前减量、专项课、比赛日冲突、阶段测试移动和赛后恢复生成候选变更；多场赛事冲突时显示优先级与取舍。取消或改期后基于**当前有效日程**重新规划，不直接恢复过期计划。
3. 展示受影响的训练/测试/休息差异并由用户确认；本任务不生成饮食或比赛补给计划。

### 5.6 AI 教练解释与对话

1. AI 教练 Tab 在有正式计划后展示快捷行动、待处理提案、计划解释和自由问答入口；无计划时继续显示建计划引导。
2. 自由问答可解释本周训练安排、训练术语、阶段建议及调整原因。聊天默认只读；若用户在对话中提出修改，必须显式进入结构化调整提案和确认流程。
3. 只提供训练领域信息与适当安全提示，不输出医疗诊断或绕过当前用户权限的内容。

### 5.7 共用提案、版本与恢复

- 复用现有 `ChangeProposal`、`TrainingPlan`、`PlanVersion`、`Workout` 和 `PlanItem`。当前提案类型、DTO、mapper、应用事务只处理单节手动课程；需扩展为一周多节课程及课程/测试/赛事相关操作，并保留旧手动接口行为。
- 提案包含基础计划版本、提案版本、变化操作白名单、受影响资源、原/新差异、阻断项、警告、生成场景、Skill/模型/规则版本及必要的输入快照。AI 来源须在课程和日历响应中准确显示，不能固定映射成 `manual`。
- 所有正式应用均重查权限、最新 FTP、时间约束、安全规则、基础版本和提案版本；使用事务、幂等键及乐观锁。重复请求只产生一次正式版本；旧提案不得覆盖新版本。
- 版本恢复先产生恢复提案并预览；确认后创建新的正式版本与审计记录，不能删除旧版本。训练历史实际记录独立保留。
- 若测试、赛事与训练尚无可共用的提案操作模型，做最小必要扩展，不把所有跨域写入塞进 AI Service。

### 5.8 结构化输出与计算边界

AI 候选至少表达训练日期、运动类型、课程目的、有序热身/工作/恢复/放松区段、时间或距离目标、工作/恢复重复关系、FTP 百分比或功率范围、训练说明、休息/测试节点、建议理由和风险标记。共享 Zod Schema 是客户端与服务端传输契约；模型输出另作为不可信输入校验，避免重复定义相互矛盾的课程结构。

FTP 功率换算、区段展开、目标时长/距离汇总、日期范围、版本差异等确定性计算由 TypeScript 完成。距离目标不伪装为确定总时长。若现有 `repeatCount` 无法无歧义地表达“工作 + 恢复”重复组，先展开为有序区段或在共享契约中明确扩展，不依赖自然语言推断。

### 5.9 建议 API 契约（以实际模块边界和 OpenAPI 为准）

| 方法             | 路径                                          | 用途                                         |
| ---------------- | --------------------------------------------- | -------------------------------------------- |
| `GET/POST`       | `/api/v1/me/ability-measurements`             | 查询/录入当前用户 FTP 测量值及来源           |
| `GET/PUT`        | `/api/v1/me/availability`                     | 查询/设置训练时间规则                        |
| `GET/POST/PATCH` | `/api/v1/goals`                               | 查询/创建/更新目标；详情、阶段可设子资源     |

| `GET`            | `/api/v1/ai-coach/readiness`                  | 当前用户 FTP、目标、时间等前置资料与缺失字段 |

| `POST`           | `/api/v1/workouts/:id/ai-adjust-proposal`     | 本节或关联范围的 AI 调整                     |

## 六、AI 调用及审核要求

所有模型调用必须复用项目已有统一 AI Gateway。

不要在业务模块中直接使用某个 AI 厂商的 SDK。

复用现有 InputGuard / OutputGuard 抽象，为可交付的生产 AI 教练补齐实际可用的审核实现；审核不可用时必须拒绝 AI 请求。当前 Noop Guard 只能用于开发和 Mock 测试，不能作为已完成的生产审核。不得为业务模块另建绕过统一 Gateway 的模型调用或平行审核链。

要求：

- 业务层不感知具体模型供应商
- 支持结构化输出
- 支持超时与错误处理
- 对返回 JSON 进行 Schema 校验
- 校验失败时提供受限制的重试或修复策略
- 不记录 API Key 或敏感的完整用户信息
- 保留必要的执行状态、错误信息与追踪标识
- 控制上下文体积及模型调用成本
- 对用户输入、Skill 内容和模型输出建立清晰的信任边界
- 对危险症状、明显不合理的训练负荷、越权指令及提示词注入建立分层拦截；普通训练讨论不能被简单关键词误伤
- 任务状态可查询；模型失败时保留原正式计划、手动课程编辑和训练记录能力
- 聊天回答与可应用提案权限分离；聊天不能直接触发 `apply`
- 保留用户、模型、Skill、Prompt、规则版本及提案/计划版本的追踪关系，敏感资料最小化记录

## 八、实施顺序与本任务不实现范围

按可独立验收的纵向闭环推进；每一步都要能在移动端和 API 验证，不能把目标/测试/赛事等核心路径永久留为接口占位：

3. **已有计划调整**：课程快捷原因、周范围调整、训练反馈与疲劳恢复建议，复用同一提案应用内核。

## 九、验收要求

开发完成后，至少验证以下场景，并报告实际运行命令与结果：

**阶段测试、赛事和解释**

**模型、安全与系统完整性**

- 模型超时、返回非 JSON、缺字段、训练规则违规、审核拒绝或任务失败时，不生成可应用提案且不修改正式计划；用户仍可查看日历及手动编辑
